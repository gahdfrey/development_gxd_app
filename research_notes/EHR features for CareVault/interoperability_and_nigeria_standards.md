# EHR Interoperability Standards and Nigeria-Specific Requirements (2025–2026) for CareVault

Scope note: research done 2026-10-03. The single most important finding is that Nigeria now has a national FHIR implementation guide, **Nigeria Core** (FHIR R4, draft, dated 2026-06-01), maintained by the Nigeria Digital in Health Initiative (NDHI) under the Federal Ministry of Health and Social Welfare (FMoHSW). Most other Nigeria-specific items (HFR API, NHIA claims exchange, NHCR/client registry, ICD-11 mandate) have thin or unverifiable official documentation. Standard, non-Nigeria-specific specs (SMART, Bulk Data, IPS, HL7 v2, DICOMweb, ASTM) are cited to canonical spec URLs; their details reflect stable, well-known spec content.

Existing CareVault state (from `lib/db/schema.ts`, checked locally): patients already carry `nin` and `mrn` columns; products carry `nafdacRegNumber`; dispense records carry `batchNumber` (for NAFDAC pharmacovigilance traceability); an `icd11_codes` table seeded from the WHO release backs diagnosis coding (`icdCode`, `icdTitle` snapshot). No FHIR, HL7 v2, LOINC, SNOMED, DICOM or DHIS2 code exists in the repo yet.

## 1. HL7 FHIR (resources, SMART, Bulk, IPS vs US Core), HL7 v2, DICOM, ASTM

### Takeaway
Target **FHIR R4 (4.0.1)**, not R5: Nigeria Core is R4 and profiles Patient, Practitioner(Role), Organization, Location, Encounter, Condition, Observation, Immunization, ServiceRequest, Medication/MedicationRequest/MedicationDispense, Coverage/Claim/ClaimResponse/EOB, Consent, Provenance, Appointment, CarePlan, Task, Invoice, Device and an **IPS-based Bundle/Composition**. Use IPS (not US Core) as the summary-document model; add SMART on FHIR/OAuth2 for auth, and keep HL7 v2/ASTM and DICOMweb as device-facing integrations for lab and radiology.

### Inferences
- **FHIR facade priority (by Nigeria Core coverage + CareVault modules):** Patient (NgPatient), Organization (NgOrganization with HFR id), Practitioner/PractitionerRole, Encounter (appointments/admissions), Condition (ICD-11 diagnoses), Observation (lab results, vitals), ServiceRequest (lab/radiology orders), DiagnosticReport + ImagingStudy (not yet profiled in Nigeria Core — use base R4/IPS), MedicationRequest/MedicationDispense/Medication (pharmacy), AllergyIntolerance (IPS), Immunization, Coverage/Claim/ClaimResponse (HMO/NHIA), Consent, Provenance, AuditEvent (map from `auditLogs`), Invoice. Expose `$everything` on Patient and an IPS `Bundle` (document) for the patient portal "download my record" and inter-facility referral.
- R5 offers nothing Nigeria requires; stay on R4 and track Nigeria Core releases (it says profiles update monthly — pin a version in CapabilityStatement).
- US Core is irrelevant beyond borrowing patterns; IPS is the international and Nigerian target for summaries.
- Implementation in Next.js: a `/api/fhir/r4/[resourceType]/[[...id]]` route mapping Drizzle rows to FHIR JSON per-tenant (`organisationId` → `Organization` + scoping), `GET /metadata` CapabilityStatement, search params `_id`, `identifier`, `patient`, `date`, `_lastUpdated`, `_count`; OAuth2 client-credentials for system-to-system (NHIA/HMO/state HIE) and SMART EHR launch for third-party apps. Bulk `$export` per tenant (Group = organisation) supports NHMIS/state analytics feeds and NDPA portability requests. Alternatively run HAPI FHIR as a sidecar and sync, but a facade avoids dual storage.
- **Lab analyzers / LIS:** most Nigerian lab instruments speak ASTM E1381/E1394 (now CLSI LIS1-A/LIS2-A2) over serial/TCP or HL7 v2.x (ORM^O01 / OML^O21 orders, ORU^R01 results, ACK). A Next.js app cannot hold serial/MLLP sockets; deploy a small on-prem "middleware/bridge" (e.g., Mirth/NextGen Connect, or a Node MLLP listener) that converts to FHIR Observation/DiagnosticReport and POSTs to CareVault. Map analyzer test codes to LOINC + UCUM units.
- **Radiology:** integrate with PACS (e.g., Orthanc, open source) via DICOM Modality Worklist (MWL C-FIND) for orders, and DICOMweb/WADO-RS + an OHIF viewer link for images; store `ImagingStudy` (StudyInstanceUID, accession number) in CareVault and the report as DiagnosticReport. Optionally HL7 v2 ORM/ORU to RIS.
- Expect FMoH licensing + conformance testing (sandbox) if the Bill passes; designing to Nigeria Core now is the low-regret path.

### Gaps
- No published (rendered) Nigeria Core IG site was reachable; `fhir-ig.digitalhealth.gov.ng` publishing status unverified. Profiles for DiagnosticReport, AllergyIntolerance, ImagingStudy, Specimen not present in repo.
- Status of the Digital Health Services Bill after first reading (2025) could not be confirmed as of Oct 2026.
- No official Nigerian requirement found for HL7 v2, ASTM or DICOM — these are industry practice, not mandates.
- National Digital Health Architecture (NDHA) PDF content not re-verified here (the project has it locally — see `reference_ndha.md` memory).

## 2. Terminologies: ICD-10/11, SNOMED CT, LOINC, RxNorm/ATC, NAFDAC

### Takeaway
Nigeria Core declares aliases for **ICD-11 MMS, SNOMED CT, LOINC and UCUM**, and uses ATC-inspired local medication codes; it maps local vaccine codes to both ICD-11 and SNOMED via ConceptMaps. For drugs, Nigeria has no RxNorm equivalent; use **ATC + NAFDAC Registration Number (NRN)** from the NAFDAC Greenbook. SNOMED licensing for Nigeria is unresolved (Nigeria is not a SNOMED member).

### Cited Findings
- Nigeria Core aliases: `$icd11 = http://id.who.int/icd/release/11/mms`, `$SCT = http://snomed.info/sct`, `$loinc = http://loinc.org`, `$ucum = http://unitsofmeasure.org`; ConceptMaps `NGVaccineLocal-to-ICD11` and `NGVaccineLocal-to-SNOMED`; local HIV status CS; device identifier VS — [alias.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/alias/alias.fsh)
- Nigeria Core medication CodeSystem `ng-atc-medication-cs` (publisher "FMoHSW / NDHI"): "Local, ATC-inspired medication codes ... placeholders" e.g. `#P01-ACT-AL` Artemether–Lumefantrine, `#G02-OXY` Oxytocin, `#J07-PENTA` Pentavalent; NgMedication marks identifier, form, ingredient (UCUM strengths), code, batch (lotNumber, expirationDate) as Must Support — [medication-codesystem.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/codesystems/medication-codesystem.fsh); [medication.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/profiles/medication.fsh)
- Local code systems also exist for Nigerian states, LGAs, wards, languages, a Nigeria vaccine library, facility types (outreach, PHC level 1/2, hospital…), relationships — [Nigeria-Core codesystems](https://github.com/digitalhealth-gov-ng/Nigeria-Core/tree/main/input/fsh/codesystems)
- SNOMED: in non-member territories, use is via an Affiliate licence through MLDS; "Charges may apply ... calculated based on use as well as the territory as determined by the World Bank"; fee exemptions possible — [snomed.org/get-snomed](https://www.snomed.org/get-snomed). Nigeria is not on the member list — [snomed.org/members](https://www.snomed.org/members). Free affiliate licences exist for World Bank **low-income** countries — [digitalhealthnews.eu](https://www.digitalhealthnews.eu/research/1451-ihtsdo-announces-free-use-of-snomed-ct-in-low-income-countries). Note: Nigeria is classified by the World Bank as **lower-middle income**, so the low-income free tier likely does not apply automatically (search-engine summaries claiming otherwise are wrong).
- ICD-11: as of May 2024, 132 member states/areas at some phase of implementation; 14 collecting/reporting data in ICD-11 — [medlearn / ICD10monitor](https://medlearn.com/icd10monitor/icd-11-in-2025-evolution-global-progress-and-what-to-watch/); WHO ICD-11 API & transition guide — [WHO ICD-11 Implementation Guide](https://icd.who.int/en/docs/ICD-11%20Implementation%20or%20Transition%20Guide_v105.pdf)
- NAFDAC Greenbook: public repository of registered drug products (7,030 entries at Jan 2024 launch), listing names, strengths, dosage forms, route and **ATC classification** and marketing authorisation details — [Nairametrics](https://nairametrics.com/2024/01/18/nafdac-unveils-greenbook-registered-drug-database-for-drug-information-access/); [greenbook.nafdac.gov.ng](https://greenbook.nafdac.gov.ng/)
- NRN format: prefix by category e.g. `A4-xxxx` drugs, `B4-` biologics/vaccines, `04-` locally manufactured, `C4-` cosmetics; older numbers 4 digits after hyphen, newer 6 digits (e.g. A4-100137) — [ogbogwu.com (non-official)](https://ogbogwu.com/nafdac-checker/) — treat as unofficial.

### Inferences
- Diagnoses: keep ICD-11 MMS (already seeded) as primary; store an optional ICD-10 crosswalk (WHO publishes ICD-10↔11 mapping tables) because NHIA/HMO tariffs and many NHMIS/IDSR forms still use ICD-10-era categories. FHIR `Condition.code.coding` can carry both.
- Lab: code every orderable/result with LOINC (free licence, globally) + UCUM units; this is a prerequisite for FHIR Observation and analyzer mapping.
- Drugs: `Medication.code` = Nigeria Core local ATC-style code or WHO ATC code + `Medication.identifier` system for NRN (CareVault's `nafdacRegNumber`); `batch.lotNumber`/`expirationDate` from dispense. Seed/refresh from Greenbook periodically (manual export/scrape; no API).
- SNOMED: use only where needed (e.g., allergy, procedure) and only after confirming an MLDS affiliate licence; otherwise rely on ICD-11 (which includes extension codes) and local value sets. Build a terminology table abstraction (`code_system`, `code`, `display`, `version`) so ConceptMaps can be added later.

### Gaps
- No official FMoH/NDHI circular found mandating ICD-11 (vs ICD-10) for Nigerian facilities or NHMIS.
- No NAFDAC Greenbook API or bulk download documented; official NRN format spec not found.
- SNOMED affiliate fee for Nigeria not published.

## 3. Nigeria specifics: NDHA/NDHI, NHCR, HFR, NIN/NIMC, NDPA/GAID, NHIA, NHMIS/DHIS2, IDSR/SORMAS

### Takeaway
Concrete hooks a Nigerian EHR should implement now: (a) Nigeria Core identifier slices on Patient (NIN, MRN, birth certificate, phone, insurance, pseudonym) and address coded to state/LGA/ward; (b) HFR facility code on every tenant/Organization; (c) NIN verification via NIMC (NVS/NINAuth, licensed access); (d) NDPA + GAID 2025 compliance (DPIA, NDPC registration/CAR filing, consent for sensitive health data); (e) NHMIS 2019 monthly summary aggregates pushable to DHIS2; (f) IDSR notifiable-disease alerts toward SORMAS/NCDC; (g) FHIR Claim/Coverage bundles for HMO/NHIA.

### Cited Findings
**Patient identity profile (NgPatient)**
- `identifier` 1..*, sliced by `type.coding.code` with slices NationalIDNo (`#NIN`, "unique 11 digit number"), MedicalRecordsNumber (`#MRN`, system = issuing institution), BirthCertificateNo (`#BIRTHCERT`, NPC), PhoneNumber (`#MOBILE`, 11 digits), InsuranceNumber (`#INSUR`, State/NHIA/HMO), Pseudonym (`#PSEUDONYM`, "one-way pseudonymized ... generated at state or national authorities e.g. NIMC"); identifier type system `https://fhir-ig.digitalhealth.gov.ng/CodeSystem/patient-identifier-cs`; `meta.lastUpdated` 1..1; `name` 1..1 with family 1..1 and given 1..*; `gender` required binding NGGenderVS; `address.district` = **LGA** (required NGLGAsVS), `address.state` required NGStatesVS; ward extension `nigeria-administrative-ward`; `contact` = caregiver with relationship VS — [patient.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/profiles/patient.fsh); [PatientExtensions.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/extension/PatientExtensions.fsh)

**Health Facility Registry (HFR)**
- National HFR manages the master facility list; states/FCT update in real time; HFR "will produce a unique facility identifier automatically following the standards agreed to by the MFL TWG"; example codes `01/01/1/1/2/0049`, `37/06/1/1/1/0336` (hierarchical: state/LGA/ownership/level/…/serial); portal offers an "request API access" option — [hfr.health.gov.ng](https://www.hfr.health.gov.ng/facilities/hospitals-list); [hfr.fmohconnect.gov.ng](https://hfr.fmohconnect.gov.ng/); [MEASURE Evaluation HFR software design](https://www.measureevaluation.org/resources/publications/tl-19-33.html); [HDC SOPs for MFL](https://www.healthdatacollaborative.org/fileadmin/uploads/hdc/Documents/Working_Groups/RHIS/B._Country-specific_documentation__case_studies__best_practices_/Data_collection_and_management/Official_RHIS_reports/Nigeria_SOPs_for_MFL.pdf)
- NgOrganization: `identifier` 1..* with `system` 1..1 (examples use `.../CodeSystem/nigeria-facility-registry`), `name` 1..1, coded `type` (facility type CS), address LGA/state, owner extension (public/private) — [organization.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/profiles/organization.fsh)
- HFR list was harmonised with the NHMIS (DHIS2) facility list — [MEASURE Evaluation TR-19-352](https://www.measureevaluation.org/resources/publications/tr-19-352.html)

**NIN verification (NIMC)**
- NIMC Verification Service (NVS): SOAP web service; verification by NIN, NIN+fingerprint, or demographics; multi-level data access; access over VPN — [NIMC Verification Service API](https://nimc.gov.ng/nimc-verification-service-api) (via search snippet; nimc.gov.ng was unreachable on fetch)
- NINAuth launched 6 May 2025 (presidential approval): web, API and mobile verification; **consent-based** — individual approves sharing for KYC; "secure, scalable, and interoperable interface for identity verification through API integration" — [Biometric Update](https://www.biometricupdate.com/202505/nigeria-unveils-platform-to-streamline-national-id-authentication-verification); [NIMC press release](https://nimc.gov.ng/press-releases/nimc-launches-nin-authentication-service-(ninauth)-for-secure-and-seamless-identity-authentication-&-verification-for-all-government-services)
- NIN verification services were disrupted and "restored nationwide" in July 2025 — [Vanguard](https://www.vanguardngr.com/2025/07/nimc-restores-nin-verification-services-nationwide/)

**NDPA 2023 + GAID 2025**
- GAID issued 20 March 2025, effective **19 September 2025** — [DLA Piper](https://privacymatters.dlapiper.com/2025/06/nigeria-ndpc-issues-gaid-key-compliance-insights/); [NDPC GAID PDF](https://ndpc.gov.ng/wp-content/uploads/2025/07/NDP-ACT-GAID-2025-MARCH-20TH.pdf)
- DPIA required when offering healthcare services and when processing sensitive data; health status is sensitive personal data; consent mandatory for certain sensitive processing; tertiary/secondary hospitals classified **Extra-High Level (EHL)** in Schedule 7 — [Lexology synopsis](https://www.lexology.com/library/detail.aspx?g=b58668ad-aac0-4149-b8df-565ae6c3ac7c) (search summary rendered "Enhanced Hasard Level"; the fee tiers are UHL/EHL/OHL, so EHL = Extra-High Level)
- Data controllers/processors of major importance register with NDPC; file Compliance Audit Returns (UHL/EHL must use a licensed DPCO); CAR filing fees ₦100,000–₦1,000,000 by volume; cross-border transfer instruments (e.g., BCRs) need Commission approval — [DLA Piper](https://privacymatters.dlapiper.com/2025/06/nigeria-ndpc-issues-gaid-key-compliance-insights/)

**NHIA / HMO claims**
- NHIA Act 2022 makes NHIA sole regulator; HMOs are NHIA-accredited TPAs handling enrolment, claims and premiums; the Act requires an extensive information/data management system — [Nigeria Health Watch](https://articles.nigeriahealthwatch.com/from-a-scheme-to-an-authority-5-things-you-need-to-know-about-the-new-nhia-act/); [HSDF NHIA brief](https://hsdf.org.ng/wp-content/uploads/2023/10/C_NHIA_KP_HCP-The-Nigerian-health-insurance-authority-3.pdf)
- NHIA and the Healthcare Federation of Nigeria agreed a joint working group on technology and data integration, as industry warned progress stalls without an integrated digital platform (2026 enrolment target context) — [Guardian NG](https://guardian.ng/news/nigeria-moves-to-scale-health-insurance-as-nhia-hfn-agree-on-2026-enrolment-target/)
- Nigeria Core defines eligibility-check, preauthorization and claim-submission/billing bundles (CoverageEligibilityRequest/Response, Claim use=preauthorization/claim, ClaimResponse, EOB, Coverage, insurer Organization) — [Nigeria-Core profiles](https://github.com/digitalhealth-gov-ng/Nigeria-Core/tree/main/input/fsh/profiles)

**NHMIS / DHIS2**
- 2019 NHMIS revision updated 13 service-delivery registers, the DHIS2 platform and disaggregation by sex/age; all 36 states + FCT transitioned by 2021; the **NHMIS Health Facility Monthly Summary Form v2019** has 19 thematic areas; aggregate data typically keyed into DHIS2 by LGA M&E officers from paper summaries — [Frontiers Digital Health 2022](https://www.frontiersin.org/journals/digital-health/articles/10.3389/fdgth.2022.985337/pdf); [Immunization Academy video](https://watch.immunizationacademy.com/en/videos/814); [FMoH NHMIS reports](https://fmohconnect.gov.ng/nhmis-annual-reports/)
- Nigeria Core plans a "Relationship with NHMIS-DHIS2" page and a `Measure` profile (page currently empty) — [Nigeria-Core repo](https://github.com/digitalhealth-gov-ng/Nigeria-Core)

**IDSR / SORMAS**
- NCDC adopted SORMAS as primary digital platform implementing IDSR for priority diseases (COVID-19 module added Jan 2020); electronic platforms improved timeliness (73% vs 43%) and completeness (≥85% vs ≤65%) vs paper; DHIS2, SORMAS, IDSR and EMRs "often operate in parallel" — [JIEPH systematic review 2026](https://afenet-journal.org/10-37432-jieph-d-26-00214/); [BMZ SORMAS study](https://health.bmz.de/studies/a-software-for-disease-surveillance-and-outbreak-response/)
- Nigeria's national IDSR technical guidelines (FMoH/NCDC) define the priority/notifiable disease list and case definitions — [NCDC IDSR guidelines PDF](https://www.ncdc.gov.ng/themes/common/docs/protocols/242_1601639437.pdf)
- 43 African nations operate IDSR, few fully aligned with WHO IDSR 3rd edition / IHR 2005 — [Scoping review PMC12958898](https://pmc.ncbi.nlm.nih.gov/articles/PMC12958898/)

### Inferences
- **Schema/feature list for CareVault:**
  - `organisations.hfrFacilityCode` (+ facility type, ownership, state/LGA codes) → required to emit NgOrganization and DHIS2 orgUnit mapping; store DHIS2 orgUnit UID separately.
  - Patient: add `birthCertificateNo`, `insuranceNumber` (+ payer), `pseudonymId`, coded `stateCode`/`lgaCode`/`wardCode` from Nigeria Core code systems; validate NIN as 11 digits (already in place) and record `ninVerifiedAt`, `ninVerificationMethod` (NVS/NINAuth/consent token), never store raw NIMC response beyond what's needed (NDPA minimization).
  - NIN verification: integrate via a licensed NIMC verification partner or NINAuth API (onboarding required); because NVS is SOAP-over-VPN, use a server-side adapter behind the existing gateway-interface pattern (like `lib/payments/gateway.ts`) with a mock for dev; NINAuth's consent model fits the existing consent module.
  - NDPA/GAID: DPIA document per tenant hospital; data-subject request workflow (exists), breach register, DPO contact per org, NDPC registration/CAR reminders, cross-border hosting decision (where the Postgres lives); log FHIR/API disclosures in `auditLogs` → FHIR AuditEvent.
  - NHMIS: build an aggregation job computing NHMIS v2019 monthly summary data elements (OPD attendance by age/sex, ANC, deliveries, immunization, malaria tests/treatment, family planning, NCD referrals, etc.) per facility-month, and push via **DHIS2 Web API `POST /api/dataValueSets`** (dataSet, orgUnit, period `YYYYMM`, dataElement/categoryOptionCombo UIDs). Mapping table: CareVault indicator → DHIS2 dataElement UID + COC UID (obtain from the national/state DHIS2 instance metadata).
  - IDSR: flag ICD-11 codes for notifiable diseases (Lassa fever, cholera, measles, CSM, yellow fever, mpox, AFP, etc. per NCDC list), generate an immediate-notification task + case-based form; export to SORMAS (SORMAS has a REST API) or provide a printable IDSR 001 form; weekly zero-reporting summary.
  - Claims: emit Nigeria Core eligibility/preauth/claim bundles from finance + Coverage tables; even before NHIA has an endpoint, HMOs increasingly accept API/portal submissions.

## 4. OpenHIE components and how African EHRs (OpenMRS, Bahmni, DHIS2) integrate

### Takeaway
OpenHIE's reference architecture — interoperability layer (OpenHIM), client registry (e.g., OpenCR), shared health record (often HAPI FHIR), terminology service (e.g., OCL), facility registry, health worker registry, and HMIS (DHIS2) — maps directly onto Nigeria Core's listed building blocks. An EHR participates as a "point-of-service" system: it submits FHIR Patient to the CR, receives a national/enterprise ID, posts encounters/IPS to the SHR, and pushes aggregates to DHIS2.

### Cited Findings
- OpenCR (IntraHealth, PEPFAR/MEASURE Evaluation): FHIR-based client registry that assigns/looks up unique IDs, accepts FHIR from EMR and lab POS systems, and links records with configurable deterministic/fuzzy/probabilistic decision rules (25 algorithm variations), with human review; in production it runs as an **OpenHIM mediator** — [OpenCR docs](https://intrahealth.github.io/client-registry/); [OpenCR algorithms](https://intrahealth.github.io/client-registry/user/algos/); [GitHub intrahealth/client-registry](https://github.com/intrahealth/client-registry)
- A Client Registry/EMPI "manages the unique identity of citizens receiving health services within the country as part of a HIE Interoperability Layer" — [NDHI-related search context / Nigeria-Core](https://github.com/digitalhealth-gov-ng/Nigeria-Core)
- Scoping review: HL7, FHIR, SNOMED CT, ICD-10/11, OpenHIE, DHIS2 and OpenMRS are the dominant tools for structural/semantic interoperability in Africa; most countries remain at pilot/sub-national scale — [PMC12958898](https://pmc.ncbi.nlm.nih.gov/articles/PMC12958898/)
- Ghana's discontinued single national EHR is cited as a lesson favouring an interoperable multi-system ecosystem over one system — [PMC12877703](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12877703/)
- OpenHIE architecture reference — [ohie.org](https://ohie.org/) / [OpenHIE Architecture Specification](https://guides.ohie.org/arch-spec)

### Inferences
- Make CareVault "OpenHIE-ready": (1) outbound FHIR client with OAuth2 client-credentials, configurable per tenant/state HIE endpoint; (2) PIX/PDQm-style patient lookup (`GET Patient?identifier=NIN|...`) against a CR; (3) store returned enterprise/CR IDs in a `patient_identifiers` table (system, value, assigner, period) instead of fixed columns — mirrors the NgPatient slice design; (4) `Bundle` transaction POST to an SHR on encounter close; (5) terminology lookups via FHIR `$lookup`/`$validate-code`/`$translate` against an OCL/Snowstorm server when national terminology services appear; (6) DHIS2 aggregate push.
- OpenMRS (via its FHIR2 module) and Bahmni (OpenMRS + Odoo + OpenELIS + dcm4chee/Orthanc PACS) are the reference stacks; their pattern of OpenELIS for LIS and dcm4chee/Orthanc for PACS validates the bridge approach in section 1. DHIS2 integration in these stacks is typically aggregate push via `dataValueSets`, or DHIS2 Tracker for case-based programmes (HIV, TB, immunization).

### Gaps
- No evidence found that Nigeria has a production national OpenHIM/OpenCR/SHR instance; Nigeria-specific OpenMRS/Bahmni deployment figures (e.g., the PEPFAR-supported NMRS — Nigeria Medical Records System, OpenMRS-based, used in HIV programmes) not verified in this pass.

## 5. Patient identity: MPI, duplicate detection/merge, biometrics in African settings

### Takeaway
Nigeria's identity anchor is the 11-digit NIN, but coverage gaps (children, unregistered adults) mean an EHR still needs a local MPI with probabilistic duplicate detection and a reversible merge/link workflow; Nigeria Core's identifier list (birth certificate, phone, insurance, pseudonym) reflects these fallbacks. Biometric verification exists through NIMC (NIN + fingerprint), but biometrics are NDPA "sensitive data" requiring explicit consent and a DPIA.

### Cited Findings
- NgPatient lists fallback identifiers including phone number and "Connectathon number" alongside NIN and MRN, and a pseudonymized identifier generated by state/national authority — [patient.fsh](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/fsh/profiles/patient.fsh)
- NVS supports verification by NIN with fingerprint and by demographic data — [NIMC Verification Service API](https://nimc.gov.ng/nimc-verification-service-api)
- NINAuth requires explicit individual consent before personal data is shared — [Biometric Update](https://www.biometricupdate.com/202505/nigeria-unveils-platform-to-streamline-national-id-authentication-verification)
- GAID/NDPA: biometric and health data are sensitive personal data; consent mandatory for certain sensitive processing — [Lexology](https://www.lexology.com/library/detail.aspx?g=b58668ad-aac0-4149-b8df-565ae6c3ac7c)
- OpenCR matching approach (deterministic + probabilistic, configurable decision rules, potential-match review queue) — [OpenCR record linkage](https://intrahealth.github.io/client-registry/user/recordlinkage/); [decision rules](https://intrahealth.github.io/client-registry/admin/decision_rules/)
- Nigeria Core security guidance: `$resolve-conflicts` SHOULD trigger manual review or return a conflict report before automated resolution — [security.md](https://github.com/digitalhealth-gov-ng/Nigeria-Core/blob/main/input/pagecontent/security.md)

### Inferences
- **MPI feature spec for CareVault (per-tenant, optionally cross-tenant for platform admin):**
  - Blocking keys: NIN (exact), phone (normalized +234), DOB ± year, Soundex/Double-Metaphone of family name, LGA.
  - Scoring: Jaro-Winkler on names (Nigerian names often reorder given/family and have transliteration variants, e.g., Mohammed/Muhammad), exact DOB, sex, phone, address LGA; thresholds → auto-link (NIN match + name ≥ 0.9), review queue (0.7–0.9), distinct. Postgres `pg_trgm` + `fuzzystrmatch` extensions can do this in-DB.
  - Merge = FHIR `Patient.link` (`replaced-by`/`replaces`) with soft-delete of the loser, re-pointing child records, full audit trail, and an un-merge path. Show a "possible duplicate" warning at registration (search before create).
  - Unique constraint on (organisationId, NIN) where NIN not null; NIN check digit — NIMC does not publish a checksum, so only length/numeric validation is possible (unverified).
- Biometrics: do not store fingerprints locally; if needed, delegate to NIMC NIN+fingerprint verification via a licensed partner, log consent, and include in DPIA. Many African programmes (e.g., PEPFAR HIV EMRs) use fingerprint matching locally, but under NDPA this raises compliance cost — prefer NIN + phone OTP + demographics.

### Gaps
- No authoritative data found on NIN enrolment coverage in 2025–2026 or on NIN issuance for minors (affects how often fallback IDs are needed).
- No source found on Nigerian guidance specifically for EHR patient-matching thresholds or biometric use in hospitals.
- Nigeria Medical Records System (NMRS) biometric practice not verified in this pass.
